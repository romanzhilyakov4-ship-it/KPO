# ВышКат — ДЗ № 1 по КПО

«ВышКат» — консольное приложение для учёта парка кикшеринга. Через меню пользователь добавляет транспорт и вещи. Перед добавлением транспорт проходит техосмотр: не прошедшие проверку транспортные средства не попадают в парк. Программа показывает количество и список имущества с уникальными инвентарными номерами, рассчитывает суммарное суточное энергопотребление и выводит транспорт, подходящий новичкам (простота управления от 6 до 10). Данные хранятся в памяти только во время работы программы.

## Запуск

Из папки `hw1`:

```bash
python main.py
```

В меню: `1` — добавить транспорт, `2` — добавить вещь, `3` — список имущества, `4` — энергопотребление, `5` — транспорт для новичков, `0` — выход.

Для проверки сценариев можно добавить исправный и неисправный транспорт, вещь, попробовать повторный номер, затем посмотреть отчёты. Данные вводятся с клавиатуры, а не задаются в коде приложения.

Тесты:

```bash
python -m pip install -r requirements.txt
python -m pytest -q --cov=main --cov=models --cov=services
```

## Структура

- `models.py` — транспорт, вещи, интерфейсы и реестры доступных типов
- `services.py` — техосмотр (`ServiceCenter`), учёт и отчёты (`Fleet`)
- `main.py` — ввод, вывод и DI-контейнер `Container`
- `test_app.py` — тесты поведения и подмены техосмотра
- `requirements.txt` — зависимости для тестов

## Архитектура и SOLID

- **S (SRP):** модели отвечают за объекты, `ServiceCenter` — за техосмотр, `Fleet` — за парк, `main.py` — за интерфейс
- **O (OCP):** новый вид транспорта добавляется в `models.py` и `VEHICLE_TYPES` без изменений `Fleet`; меню само запрашивает поля типов `str`, `int`, `float`
- **L (LSP):** наследники `Vehicle` одинаково обрабатываются сервисом `Fleet`
- **I (ISP):** инвентаризация, потребление энергии и техосмотр описаны отдельными интерфейсами
- **D (DIP):** `Fleet` получает зависимость `Inspector` через конструктор, а `Container` связывает реализации

**Наиболее явно применён DIP:** `Inspector` и `Fleet.__init__()` в `services.py`, регистрация зависимостей в `Container` (`main.py`).

**Сознательно ограничен SRP:** `Fleet` совмещает учёт и несколько простых отчётов. Выделять отдельный сервис отчётов для этого небольшого проекта не требуется. Критерий техосмотра `condition >= 5` выбран как учебное правило, так как в задании порог не задан.

**Расширение:** новый транспорт — наследник `Vehicle` или `PoweredVehicle` и запись в `VEHICLE_TYPES`; `Fleet` изменять не нужно. Сотрудники не относятся к инвентарю: для них понадобится отдельная модель и сервис. Для склада запчастей потребуется отдельный учёт остатков.

**Тестирование:** `test_inspection_threshold` проверяет техосмотр, `test_beginner_threshold` — правило для новичков, `test_inspector_replaced_through_container` — подмену техосмотра через `Container.bind()` и `Mock`. `test_console_all_scenarios_from_input` проверяет работу с консольным вводом.

**Использование ИИ:** ИИ использовался при написании юнит-тестов, оформлении README, а также для консультаций по отдельным вопросам реализации на Python. Работоспособность приложения и тестов проверялась локально.
